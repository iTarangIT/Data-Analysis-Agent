# Tarang — Level 1 AI Data Analyst Agent

Single Next.js app (App Router) — one repo, one Node.js runtime. Full architecture: docs/ARCHITECTURE.md (SAD v3.1). Read the relevant section before large changes; never re-derive decisions already made there.

## Stack
Next.js 16 + React 19 · TypeScript · LangChain JS (prebuilt agent from @langchain/langgraph) · OpenAI/OpenRouter · Playwright (Node) · Prisma + PostgreSQL · Zod · Clerk · Inngest · Pino · LangSmith

## Commands
- `npm run dev` — run locally
- `npm run build && npm start` — production build
- `npm run lint` — ESLint
- `npm run db:migrate` — create/apply a migration · `db:status`, `db:deploy`, `db:generate`
- `npm run db:studio` — inspect the DB
- `npm run auth:login` — verify Intellicar authentication end to end
- `npm run portal:fetch [module]` — read a live dashboard module through the Portal Service (defaults to `fleet_overview`)

## Hard rules — never violate
1. The agent NEVER touches credentials, cookies, tokens, or Playwright storageState. Only `src/services/credentials/` and `src/services/session/` may. Authentication is never agent-callable at any level — no tool, no registry entry, no prompt text. A service asks `withAuthenticatedContext()` for a context; a tool never does. Enforced in both directions by the import zones in `eslint.config.mjs`.
2. Every tool result is wrapped by the Tool Registry in the source envelope `{ data, source: { tool, origin, params, timestamp } }`. Numeric claims in answers must cite envelope sources from tool calls that actually ran — never invented ones. `origin` always names the source that ANSWERED; when more than one was consulted the source also carries `contributingSources[]` (Milestone 5D-4), built mechanically from the reconciliation and absent for single-source results. The tool declares the attribution's content; the registry owns its shape.
3. `/api/chat` runs ONLY the interactive agent loop. Everything else (reports, scheduled sync, email, approvals) is emitted as an Inngest event.
4. The Playwright browser and PrismaClient are `globalThis` singletons.
5. The agent's raw SQL path is SELECT-only, executed under the read-only DB role.
6. Exactly 4 tools at Level 1: portal, database, analysis, report. No new tools or speculative folders without updating docs/ARCHITECTURE.md first.

## Conventions
- Route Handlers stay thin: auth → Zod validation → service call → stream. Logic lives in `src/services/<name>/`.
- Tools in `src/tools/` are thin adapters over services — no scraping, SQL, or rendering inside a tool.
- Prisma: schema at `prisma/schema.prisma`, CLI config at `prisma.config.ts` (loads `.env.local` — `DATABASE_URL` has exactly one home, never a committed default). Generated client at `src/generated/prisma`, gitignored and rebuilt by `postinstall`. Telemetry is imported manually — no seed script (docs/DATA-IMPORT.md).
- Secrets come only from env, validated in `src/lib/env.ts` — eagerly for application config, lazily via `authEnv()` for the Intellicar domain, so the telemetry path never depends on portal configuration. Never log secrets; Pino redaction in `src/lib/logger.ts` covers credentials, cookies, storageState and authorization headers. Redaction matches field *paths*, not free text, so never interpolate a secret into a message.
- Intellicar authentication (docs/AUTH-SETUP.md): the Session Manager owns authentication and `session-manager.ts` is its only public entry point; every URL and selector of the LOGIN FLOW lives in the one `INTELLICAR` constants block in `authenticator.ts`, where `TODO(intellicar)` marks values still unverified against the live portal.
- Live dashboard extraction is owned by the Portal Service, and each dashboard module's path and selectors live with that module in `src/services/portal/extractors/` — never in `authenticator.ts`, which knows only how to sign in. `portal.service.ts` is the only caller of `withAuthenticatedContext()`; extractors only read a page they are handed, `normalizers.ts` is pure and never imports Playwright, and Zod validates every normalized result. Enforced by the Portal zone in `eslint.config.mjs`.
- The portal is a client-rendered SPA: its data arrives well after `domcontentloaded`, and `networkidle` never settles. A capability declares readiness selectors targeting a *data-bearing* element; the Portal Service navigates and waits, extractors never do either. Capture a raw extraction into `src/services/portal/fixtures/` when adding a module, so its normalizer stays runnable without a portal.
- A module that reports one entity is a TARGETED capability (`targeted: true`, Milestone 4C): the portal exposes no per-vehicle route, so it declares `resolve()` — an in-page phase the Portal Service runs between navigation and readiness — and `assertIdentity()`, which the compiler requires alongside it. An ACCOUNT-WIDE module declares neither (`fleet_overview`, `battery_analytics`). Extractors stay read-only; the rule they obey is NEVER MUTATE, so navigating a view or paging a table is allowed, while submitting a form, saving a setting or issuing a device command is not.
- The Analysis Engine (`src/services/analytics/`, Milestone 5B) is the only module that may hold two source classes at once, and it is a SERVICE — reached in-process by `analysis.tool.ts`, never registered as a tool. It sits ABOVE the Portal and Database services and depends on both; neither depends on it, and the Analytics zone in `eslint.config.mjs` enforces that direction plus the usual bans (no session, no credentials, no Playwright, no Prisma, no tool or agent layer). Six stages: plan → vocabulary → acquire → reconcile → compute → assemble. Only `acquisition.ts` performs I/O; `observations.ts`, `projections.ts`, `reconcile.ts`, `series.ts` and `conflict.ts` are pure and run against `fixtures/` with no database or portal — the purity zone bans modules that can start a browser or open a connection, not whole directories, so `portal/normalizers.ts` (pure parsing) is importable while `portal.service` and `extractors/` are not. THE ENGINE NEVER CALLS AN LLM — it decides which source answers, and the model narrates the decision. A quantity's historical feed is SAD §19's table restated, never reassigned; `sourceClass` is a separate axis. A reported value has exactly one provider: two sources are never averaged, and a losing candidate is kept as an alternative rather than discarded.
- A COMPUTED value carries a `Derivation` (Milestone 5C): the operation, the absolute window, the row and distinct-measurement counts, the span, and whether the read was truncated. It is attached even when the computation failed — that is the INSUFFICIENCY CONTRACT: an empty window, unusable rows, or too few measurements return an unavailable Observation with a reason, never an exception. What still throws is a question that cannot be asked (a derivation over a position, an inverted window, an unknown vehicle). Windows reaching the engine are always ABSOLUTE: resolving "the last N days" needs a clock, and the single clock read lives in `analysis.tool.ts` so the engine stays deterministic. Samples are collapsed by measurement instant, because a CAN signal re-reported unchanged across rows is one measurement, not several.
- A quantity may declare a LIVE provider (Milestone 5D), and the compiler then requires a `reconciliation` spec beside it — a live provider without a declared notion of disagreement is unrepresentable. A live reading's `measuredAt` is the portal's Last Talk Time, never `capturedAt`: the first is when the vehicle reported, the second is when we looked. `conflict.ts` reports a disagreement only when both sources are available and differ by more than the calibrated threshold, and tests it against a declared plausible rate over the gap between the two measurements — never against the current time, which would break determinism. Age explanation is three-state (`explained` / `unexplained` / `unknown`); an unknown age is reported, never escalated. Thresholds and rates are calibrated from measurement and recorded with the observation that produced them. Fuel stays Fuel: read the portal's own name, never reinterpret it.
- Precedence (Milestone 5D-3): **P1** a current question prefers live, a windowed one is historical-only and makes no portal call; **P2** §19's authoritative feed within the historical class; **P4** a live reading OLDER than the recorded one is demoted — applied in `reconcile.ts`, not the planner, because it needs measurement times, and it never fires on an unknown time; **P5** an unavailable source substitutes and the rule NAMES the substitution. P3/P6/P7 are structural, P0 waits for 5E. `acquisition.ts` is the ONLY file that reaches the portal, via `fetchPortalModule` exactly as the Portal Tool does; a portal failure becomes an unavailable live observation (never a throw — Postgres is the system of record, the portal is a corroborator). The tool emits a `reconciliation` block only when more than one source was consulted, so everything else stays byte-identical, and it declares `timeoutMs` 120s to cover a portal leg.
- Telemetry record shapes and conversions live in `src/services/database/telemetry.records.ts` (no I/O, so the engine's pure files may import it) and the reads in `telemetry.reader.ts`. `src/tools/database.tool.ts` is the §6 adapter over them.
- Every module starts with a DISCOVERY PASS against the live portal, and the design follows what it finds, not the other way round (Milestone 4D). Selectors and catalogues are read off the rendered DOM and stamped `VERIFIED against the live portal on <date>`; never guessed. When discovery contradicts an approved design, it is the design that changes — 4D was approved as per-vehicle Battery Telemetry and became fleet-wide Battery Analytics because the portal has no per-vehicle battery view. Match rows and fields by their rendered LABEL, never by position: the battery rows render in a DOM order that differs from their on-screen order.
- Prefer editing existing files over creating new ones; keep the project tree matching docs/ARCHITECTURE.md Section 18, with one deliberate deviation: the App Router lives at `src/app/`, not the root `app/` shown in Section 18. Everything else under `src/` matches. Route Handlers therefore live at `src/app/api/<name>/route.ts`.
