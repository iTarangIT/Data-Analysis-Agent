# Tarang — Level 1 AI Data Analyst Agent

Single Next.js app (App Router) — one repo, one Node.js runtime. Full architecture: docs/ARCHITECTURE.md (SAD v3.1). Read the relevant section before large changes; never re-derive decisions already made there.

## Stack
Next.js 16 + React 19 · TypeScript · LangChain JS (prebuilt agent from @langchain/langgraph) · OpenAI/OpenRouter · Playwright (Node) · Prisma + PostgreSQL · Zod · Pino · LangSmith · **self-hosted sealed-cookie auth (NOT Clerk, NOT Auth.js — see SAD §10)** · Inngest *(planned, not installed)*

## Commands
- `npm run dev` — run locally
- `npm run build && npm start` — production build
- `npm run lint` — ESLint
- `npm run db:migrate` — create/apply a migration · `db:status`, `db:deploy`, `db:generate`
- `npm run db:studio` — inspect the DB
- `npm run auth:login` — verify Intellicar authentication end to end
- `npm run portal:fetch [module]` — read a live dashboard module through the Portal Service (defaults to `fleet_overview`)

## Hard rules — never violate
1. The agent NEVER touches credentials, cookies, tokens, or Playwright storageState. Only `src/services/credentials/` and `src/services/session/` may. Authentication is never agent-callable at any level — no tool, no registry entry, no prompt text. A service asks `withAuthenticatedContext()` for a context; a tool never does. Enforced in both directions by the import zones in `eslint.config.mjs`.
2. Every tool result is wrapped by the Tool Registry in the source envelope `{ data, source: { tool, origin, params, timestamp } }`. Numeric claims in answers must cite envelope sources from tool calls that actually ran — never invented ones. `origin` always names the source that ANSWERED; when more than one was consulted the source also carries `contributingSources[]` (Milestone 5D-4), built mechanically from the reconciliation and absent for single-source results. The tool declares the attribution's content; the registry owns its shape.
3. `/api/chat` runs ONLY the interactive agent loop. Everything else (reports, scheduled sync, email, approvals) is emitted as an Inngest event.
4. The Playwright browser and PrismaClient are `globalThis` singletons.
5. The agent's raw SQL path is SELECT-only, executed under the read-only DB role.
6. Exactly 4 tools at Level 1: portal, database, analysis, report. No new tools or speculative folders without updating docs/ARCHITECTURE.md first.
7. The agent NEVER writes long-term memory. Long-term memory is USER-OWNED DATA: only an explicit, authenticated user action through `/api/memory` may create, update or delete an entry — there is no memory tool, and adding one would breach rule 6 and hand prompt injection a write primitive. The agent READS approved memory and nothing more, and memory must never contain a telemetry measurement, a tool result or portal data. `ownerId` is ALWAYS the server-derived `OwnerId` from the sealed session cookie (SAD §10) — never a value from a body, query, header, or browser storage. NO ANONYMOUS MEMORY: no principal means no `OwnerId` means no row. PostgreSQL and Intellicar remain authoritative for every operational number; memory never substitutes for them.
8. The run context (Phase 4A) carries WHAT A TURN ASKED, never WHAT IT MEASURED. It is built only from `ToolEnvelope.source` of tool calls that actually ran; `envelope.data` is never read, so no SoC, SoH, temperature, location, speed, fleet count or portal payload can enter it. It RESOLVES A REFERENCE and never answers one: a figure reported earlier in a conversation is never a figure that may be reported now, and the tool is always called again for the value. Long-term memory does not exist — there is no UserMemory table, no Memory Manager and no write path, and none may be added without app authentication (SAD §7, §19).

## Conventions
- Route Handlers stay thin: auth → Zod validation → service call → stream. Logic lives in `src/services/<name>/`.
- Tools in `src/tools/` are thin adapters over services — no scraping, SQL, or rendering inside a tool.
- Prisma: schema at `prisma/schema.prisma`, CLI config at `prisma.config.ts` (loads `.env.local` — `DATABASE_URL` has exactly one home, never a committed default). Generated client at `src/generated/prisma`, gitignored and rebuilt by `postinstall`. Telemetry is imported manually — no seed script (docs/DATA-IMPORT.md).
- Secrets come only from env, validated in `src/lib/env.ts` — eagerly for application config, lazily via `authEnv()` for the Intellicar domain, so the telemetry path never depends on portal configuration. Never log secrets; Pino redaction in `src/lib/logger.ts` covers credentials, cookies, storageState and authorization headers. Redaction matches field *paths*, not free text, so never interpolate a secret into a message.
- Intellicar authentication (docs/AUTH-SETUP.md): the Session Manager owns authentication and `session-manager.ts` is its only public entry point; every URL and selector of the LOGIN FLOW lives in the one `INTELLICAR` constants block in `authenticator.ts`, where `TODO(intellicar)` marks values still unverified against the live portal.
- Live dashboard extraction is owned by the Portal Service, and each dashboard module's path and selectors live with that module in `src/services/portal/extractors/` — never in `authenticator.ts`, which knows only how to sign in. `portal.service.ts` is the only caller of `withAuthenticatedContext()`; extractors only read a page they are handed, `normalizers.ts` is pure and never imports Playwright, and Zod validates every normalized result. Enforced by the Portal zone in `eslint.config.mjs`.
- The portal is a client-rendered SPA: its data arrives well after `domcontentloaded`, and `networkidle` never settles. A capability declares readiness selectors targeting a *data-bearing* element; the Portal Service navigates and waits, extractors never do either. Capture a raw extraction into `src/services/portal/fixtures/` when adding a module, so its normalizer stays runnable without a portal.
- A module that reports one entity is a TARGETED capability (`targeted: true`, Milestone 4C): the portal exposes no per-vehicle route, so it declares `resolve()` — an in-page phase the Portal Service runs between navigation and readiness — and `assertIdentity()`, which the compiler requires alongside it. An ACCOUNT-WIDE module declares neither (`fleet_overview`, `battery_analytics`). Extractors stay read-only; the rule they obey is NEVER MUTATE, so navigating a view or paging a table is allowed, while submitting a form, saving a setting or issuing a device command is not.
- The Analysis Engine (`src/services/analytics/`, Milestone 5B) is the only module that may hold two source classes at once, and it is a SERVICE — reached in-process by `analysis.tool.ts`, never registered as a tool. It sits ABOVE the Portal and Database services and depends on both; neither depends on it, and the Analytics zone in `eslint.config.mjs` enforces that direction plus the usual bans (no session, no credentials, no Playwright, no Prisma, no tool or agent layer). Six stages: plan → vocabulary → acquire → reconcile → compute → assemble. Only `acquisition.ts` performs I/O; `observations.ts`, `projections.ts`, `reconcile.ts`, `series.ts` and `conflict.ts` are pure and run against `fixtures/` with no database or portal — the purity zone bans modules that can start a browser or open a connection, not whole directories, so `portal/normalizers.ts` (pure parsing) is importable while `portal.service` and `extractors/` are not. THE ENGINE NEVER CALLS AN LLM — it decides which source answers, and the model narrates the decision. A quantity's historical feed is SAD §19's table restated, never reassigned; `sourceClass` is a separate axis. A reported value has exactly one provider: two sources are never averaged, and a losing candidate is kept as an alternative rather than discarded.
- A COMPUTED value carries a `Derivation` (Milestone 5C): the operation, the absolute window, the row and distinct-measurement counts, the span, and whether the read was truncated. It is attached even when the computation failed — that is the INSUFFICIENCY CONTRACT: an empty window, unusable rows, or too few measurements return an unavailable Observation with a reason, never an exception. What still throws is a question that cannot be asked (a derivation over a position, an inverted window, an unknown vehicle). Windows reaching the engine are always ABSOLUTE: resolving "the last N days" needs a clock, and the single clock read lives in `analysis.tool.ts` so the engine stays deterministic. Samples are collapsed by measurement instant, because a CAN signal re-reported unchanged across rows is one measurement, not several.
- A quantity may declare a LIVE provider (Milestone 5D), and the compiler then requires a `reconciliation` spec beside it — a live provider without a declared notion of disagreement is unrepresentable. A live reading's `measuredAt` is the portal's Last Talk Time, never `capturedAt`: the first is when the vehicle reported, the second is when we looked. `conflict.ts` reports a disagreement only when both sources are available and differ by more than the calibrated threshold, and tests it against a declared plausible rate over the gap between the two measurements — never against the current time, which would break determinism. Age explanation is three-state (`explained` / `unexplained` / `unknown`); an unknown age is reported, never escalated. Thresholds and rates are calibrated from measurement and recorded with the observation that produced them. Fuel stays Fuel: read the portal's own name, never reinterpret it.
- Precedence (Milestone 5D-3): **P1** a current question prefers live, a windowed one is historical-only and makes no portal call; **P2** §19's authoritative feed within the historical class; **P4** a live reading OLDER than the recorded one is demoted — applied in `reconcile.ts`, not the planner, because it needs measurement times, and it never fires on an unknown time; **P5** an unavailable source substitutes and the rule NAMES the substitution. P3/P6/P7 are structural, P0 waits for 5E. `acquisition.ts` is the ONLY file that reaches the portal, via `fetchPortalModule` exactly as the Portal Tool does; a portal failure becomes an unavailable live observation (never a throw — Postgres is the system of record, the portal is a corroborator). The tool emits a `reconciliation` block only when more than one source was consulted, so everything else stays byte-identical, and it declares `timeoutMs` 120s to cover a portal leg.
- A quantity has a SCOPE (Milestone 5E), and it is a third axis that amends neither §19's feed table nor `sourceClass`: it decides what an answer is ABOUT — one vehicle, or the population. Fleet quantities are separate `fleet_*` registry entries, never a flag on a per-vehicle one, and an aggregate names its `memberQuantity` rather than restating a table, so §19 is referenced and never copied. **P0** is the scope gate and lives in the PLANNER — both its inputs are static, so a mismatch is refused before any read, and it is not a `PrecedenceRule` because it selects nothing. A fleet answer carries an `Aggregation`: a SIBLING of `Derivation`, never an extension, recording whether the number was `reported` by the dashboard, `aggregated` across members, or `counted` from the registry — plus, for an aggregate, COVERAGE (contributing vehicles out of the population) and the SPAN of the contributing measurements, which reaches 59 days on this fleet because CAN is a last-known-value snapshot. Thin coverage is answered with its numbers, never refused. One vehicle contributes one sample (`aggregate.ts`), the fleet counterpart of collapsing a re-reported CAN signal. The population is resolved ONCE per run and the reads are scoped to it, so the numerator and denominator describe the same fleet; the engine walks the population, not the readings, so a silent vehicle is a counted non-contributor rather than a vanished one. THE ONE-READ RULE: a fleet-scope live provider must be an account-wide module and passes no target, and a fleet historical read is one `DISTINCT ON` query for every vehicle — never one scrape or one query per vehicle. Fleet windows are modelled (`MemberDerivation`) and refused in the planner. `fleet_size` compares two registries with `comparison: "count"`, whose age is `not_applicable` rather than `unknown`, and reports 320 vs 70 as genuinely DISPUTED.
- Telemetry record shapes and conversions live in `src/services/database/telemetry.records.ts` (no I/O, so the engine's pure files may import it) and the reads in `telemetry.reader.ts`. `src/tools/database.tool.ts` is the §6 adapter over them.
- Every module starts with a DISCOVERY PASS against the live portal, and the design follows what it finds, not the other way round (Milestone 4D). Selectors and catalogues are read off the rendered DOM and stamped `VERIFIED against the live portal on <date>`; never guessed. When discovery contradicts an approved design, it is the design that changes — 4D was approved as per-vehicle Battery Telemetry and became fleet-wide Battery Analytics because the portal has no per-vehicle battery view. Match rows and fields by their rendered LABEL, never by position: the battery rows render in a DOM order that differs from their on-screen order.
- Short-term conversation memory is the browser's transcript plus a structured RUN CONTEXT (Phase 4A/4B, SAD §15). `src/lib/turn-context.ts` derives `TurnContext` — `subjects[]`, `metrics[]`, optional `window`, each most-recent-first and capped at 3, so element 0 IS "the last one" and there is no second field holding the same value — from the `tool_result` envelopes the client already holds. A failed envelope establishes nothing. `/api/chat` re-validates it as UNTRUSTED input (identifier `[A-Za-z0-9._-]{1,64}`, metric `[a-z0-9_]{1,64}` — patterns that exclude whitespace so an injected sentence is unrepresentable), adds the run's single clock read as `now`, and passes it through `configurable`; the agent's `prompt` FUNCTION is the only reader, and `withRunContext(undefined)` returns SYSTEM_PROMPT byte-for-byte so a context-free run is unchanged. Nothing below the agent — no tool, no registry, no service, no engine — knows it exists. THE STREAMING PROTOCOL IS UNCHANGED: no frame was added, because `tool_result` already carried what was needed and the context travels up the wire in the request body instead. `SYSTEM_PROMPT_VERSION` is 1.3.0; bump it whenever the prompt contract changes, and keep the block deterministic so LangSmith traces stay comparable.
- History is bounded (Phase 4B, SAD §15). `src/lib/history.ts` is the third bound on a run, after `AGENT_RECURSION_LIMIT` and `TOOL_TIMEOUT_MS`: `MAX_HISTORY_MESSAGES` 20 and `MAX_MESSAGE_CHARS` 16,000. A long history is TRIMMED — oldest first, the window realigned to start on a question, applied by the client and again by the route with the same function so the route's pass is a no-op for the UI and a real ceiling for anything else. An over-long single message is REJECTED with a 400, because truncating it would answer a question the user did not ask. Never summarise dropped turns: a summary is model prose, and prose re-read later is indistinguishable from a tool result — the fabricated citation rule 2 exists to prevent.
- Application identity is a SELF-HOSTED SEALED COOKIE (Phase 4D, SAD §10) — not Clerk, not Auth.js, no external provider, and no `middleware.ts`. `src/services/identity/` owns it: `users.ts` (scrypt + `timingSafeEqual` over `APP_USERS`), `app-session.ts` (AES-256-GCM via the generic `credentials/crypto.ts`, AAD `tarang.app-session.v1`), `principal.ts` (the ONLY place an identity enters the system, and the only constructor of the branded `OwnerId`). Config is a fourth lazy env schema: `APP_AUTH_ENABLED` (default false), `APP_SESSION_KEY` (never `CREDENTIAL_ENCRYPTION_KEY`), `APP_USERS`, `APP_SESSION_TTL_HOURS`. `APP_USERS` records are `name:scrypt.N.r.p.salt.hash` separated by `;` — DOT-delimited, never `$`, because `.env` interpolation gutted every `$…` segment and made every sign-in fail; mint one with `npm run app:user -- <name>`. Enforcement is at the route, before the body is read. This is NOT `src/services/session/`, which is Intellicar's browser session — `IDENTITY_ZONE` keeps them apart in both directions. As of Phase 4F the SIGN-IN AND LOGOUT CONTROLS EXIST: `src/app/page.tsx` is a Server Component that reads `getAppPrincipal()` and passes `authEnabled` + `userId` to `src/components/chat/ChatSurface.tsx` (the former page body, streaming logic unchanged) — the cookie is HttpOnly, so the client cannot answer "am I signed in" itself. It adds NO new endpoint: sign-in is a link to the existing `/sign-in`, logout POSTs the existing `/api/auth/logout` then does a FULL navigation because the cookie changed. `dynamic = "force-dynamic"` on the page is load-bearing — the disabled path never touches cookies, so Next would otherwise bake the BUILDER's `APP_AUTH_ENABLED` into a prerendered page. `APP_AUTH_ENABLED=false` renders neither control.
- Long-term memory is BUILT (Phase 4E, SAD §7). `MemoryEntry { id, ownerId, kind, value, source, createdAt, updatedAt }` with `@@unique([ownerId, kind])` — one value per preference per user, so an update REPLACES and conflicts are unrepresentable rather than reconciled. Kinds are exactly `preferred_vehicle`, `preferred_metric`, `default_window_days`, `report_style`; sources are `user_stated` and `user_confirmed`, with no `inferred`. Value schemas are `.strict()`, so a stray telemetry field is refused rather than stripped, and there is no free-text kind. `src/services/memory/memory.service.ts` is the ONLY caller of `prisma.memoryEntry`, and every function takes `OwnerId` first — there is no zero-argument read, so a cross-user query cannot be written. Retrieval happens in `/api/chat` beside the agent, reaching the model through the Phase 4A `configurable`/prompt seam: **no new stream frame, `ChatStreamFrame` unchanged, never sent as a `tool_result`**. No feature flag — an empty table is the off switch. Production migration on Railway is a MANUAL step and gates the feature; `docker-entrypoint.sh` runs none, so run `prisma migrate deploy` BEFORE enabling `APP_AUTH_ENABLED`.
- Memory validation is SPLIT ACROSS TWO LAYERS (Phase 4F). The service owns SHAPE (`.strict()` Zod, write and read); the ROUTE owns EXISTENCE — `preferred_vehicle` must name a row in `vehicles`, `preferred_metric` must be a member of `QUANTITIES` — because MEMORY_ZONE forbids the memory service from importing the Database Service, the Portal Service or the Analysis Engine, and the zone's own comment already prescribes that the route do it and hand memory an already-validated value. A nonexistent reference is a 400 that names what it rejected. Never move either half into the other layer. `ownerId` IS THE `APP_USERS` NAME, not a stable id, and rows outlive a user's removal from `APP_USERS` — so a reused name inherits the previous owner's preferences and a name must be treated as permanent.
- The memory prompt block states a CLOSED VOCABULARY (Phase 4F, `SYSTEM_PROMPT_VERSION` 1.5.0). 4E listed what was stored without saying the list was exhaustive, so "my preferred battery" — not a kind that exists — resolved to the nearest neighbour and reported the preferred VEHICLE. The block now says the four kinds are all there are, that one may never be read as another, and that an unlisted preference must be reported as NOT STORED rather than substituted. `report_style` is rendered as an explicit AMENDMENT to the Style section (`brief` confirms it, `detailed` replaces "keep it brief"), never as a bare line beside it — two live instructions with no rule for choosing was the 4E bug. `withRunContext(undefined)` still returns SYSTEM_PROMPT byte for byte.
- `npm run memory:check` (Phase 4F, `scripts/memory-check.ts`) verifies the whole of the above against a locally running app: lifecycle across all four kinds, logout/login persistence, two-user isolation including an adversarial cross-owner delete, the route's write guards, and the prompt rules. It MINTS its own sealed cookies for two namespaced synthetic owners rather than using a password, so no test credential exists to leak or clean up, and it NEVER calls OpenRouter — prompt behaviour is asserted against `withRunContext`, which is pure. Scaffolding, like `auth-login.ts` and `app-user.ts`: no route, no tool, no registry entry.
- Prefer editing existing files over creating new ones; keep the project tree matching docs/ARCHITECTURE.md Section 18, with one deliberate deviation: the App Router lives at `src/app/`, not the root `app/` shown in Section 18. Everything else under `src/` matches. Route Handlers therefore live at `src/app/api/<name>/route.ts`.
